このファイルが、App Store の Product Page Optimization（PPO）、カスタムプロダクトページ、オンボーディング、ペイウォールなど、すべての実験の完了条件である。個別の実験メモは、この条件を引用し、仮説と指標だけを足す。

## 1テスト、1面、連続して回す

- アプリごと、面ごとにライブの実験は常に1つだけ（PPO は Apple も同時に1件まで）。
- 走っている実験を止めて別の実験を立てない。次の仮説はバックログに並べ、結果が出た当日に次を出す。
- 最低7日は走らせてから判定する。7日未満では勝敗を付けない。
- 判定に使う信頼度は、App Store Connect の PPO が示す数値を使う（自前で有意差を計算して上書きしない）。

## 完了条件（必ずどれかで閉じる）

1. **勝ち（Winner）**  
   ASC PPO が、トリートメントの改善を信頼度 90% 以上で示す。  
   → トリートメントをデフォルトのプロダクトページに適用する。同じ日に次のテストを開始する。

2. **負け（Loser）**  
   コントロールが信頼度 90% 以上で勝つ。  
   → 実験を止める。コントロールを残す。同じ日に次のバリアントを開始する。

3. **結論なし（Inconclusive）**  
   14日（または Apple の上限の早い方）に達しても 90% に届かない。  
   → 実験を止める。より安く、より分かりやすい方を残す（通常は現行コントロール。トリートメントの方が制作・運用コストが明らかに低い場合のみ入れ替える）。結果ログに `inconclusive` と書く。次は、より大きい変更（コピーだけならレイアウト、レイアウトならファーストショットの題材、など）でテストする。

判定指標の既定値は、PPO では **コンバージョン（プロダクトページ閲覧 → 初回ダウンロード）**。オンボーディングとペイウォールは、各実験メモに指標を書く（トライアル開始、有料化、またはその両方）。下流の返金・解約も見るが、完了条件の主指標にはしない。

## 結果ログ（必須）

各実験の終了時に、実験メモと `team/TEAM-FEED.md` へ次を残す。

| 項目 | 書くこと |
|---|---|
| アプリ / 面 | 例: Anicca / PPO screenshots / en-US |
| 実験 ID と名前 | ASC の id と名称 |
| 期間 | 開始日と終了日（JST）、実走日数 |
| インプレッション | コントロールとトリートメント |
| CVR | コントロール vs トリートメント |
| 信頼度 | ASC が表示した % |
| 判定 | Winner / Loser / inconclusive |
| 次に出すテスト | バックログのどれを、いつ出すか |

秘密・トークン・審査用メモは書かない。

## 手順の要点

- 仮説は1変数にする（例: 見出し文言だけ、1枚目の題材だけ）。レイアウトとコピーを同時に変えない。
- コントロールは、その時点の公開プロダクトページ（または現行のオンボ / ペイウォール）。
- フェイチャー（実在しない画面、盛った評価数、未実装の機能）は使わない。
- 文言・スクショ・ペイウォールの変更は、有料ツールを使わず、`bash /workspace/team/scripts/ascx.sh` で確認して提出する。
